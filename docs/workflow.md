# opendatahackathon42

Team repository for the Open Data Hackathon project "Słuchowisko".

| Environment | URL                                           | Built from    |
| ----------- | --------------------------------------------- | ------------- |
| Production  | http://ggrzesiek.dev/opendatahackathon42/     | `release`     |
| Development | http://ggrzesiek.dev/opendatahackathon42/dev/ | `development` |

## Branches

```
feature/* ──PR (rebase)──▶ development ──CI passes → Promote to release (fast-forward)──▶ release
```

| Branch        | Purpose                                                                                  | How it changes                                                                                        |
| ------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `development` | Default branch. Integration of all finished work. Deployed to `/dev/`.                   | Only through pull requests, merged with rebase.                                                       |
| `release`     | Production. Deployed to `/`.                                                             | Only through the **Promote to release** workflow, run automatically after CI passes on `development`. |
| `feature/*`   | Your work. Also `fix/*`, `docs/*`, `ci/*`.                                               | Push freely. Deleted automatically after merge.                                                       |
| `gh-pages`    | Built website, generated by CI. Not part of the workflow; do not edit or branch from it. | Overwritten on every deploy.                                                                          |

## Day-to-day workflow

1. Pick an issue and assign yourself.
2. Start from the latest `development`:
   ```bash
   git switch development
   git pull
   git switch -c feature/<issue-number>-<short-name>
   ```
3. Commit in small steps. Write commit messages in English.
4. Before pushing, run the formatters and linters (see [Checks](#checks)).
5. Keep your branch up to date by rebasing, never by merging:
   ```bash
   git fetch
   git rebase origin/development
   git push --force-with-lease
   ```
6. Open a pull request into `development`. Write the title and description in English and link the issue (`Closes #12`).
7. When all checks are green and review threads are resolved, merge with **Rebase and merge**. The branch is deleted automatically.
8. A few minutes later the change is live on `/dev/`.

Make `git pull` rebase instead of merge, once per clone:

```bash
git config pull.rebase true
```

## Merge rules

Enforced by GitHub rulesets:

- `development`
  - changes only through a pull request; no direct pushes
  - **Rebase and merge** only; linear history
  - all CI checks must pass
  - all review conversations must be resolved
  - no force pushes, no deletion
- `release`
  - no direct pushes, except by the promotion workflow and the repository admin
  - fast-forward only, linear history, no deletion

Approvals are not required, but asking a teammate to look at your PR is encouraged.

## Checks

CI runs on every pull request and on every push to `development` and `release`.

| Check                       | What it does                                      | Fix locally                                                           |
| --------------------------- | ------------------------------------------------- | --------------------------------------------------------------------- |
| Python (ruff)               | Lint and formatting of Python code                | `pipx run ruff==0.6.9 check --fix . && pipx run ruff==0.6.9 format .` |
| Python tests (pytest)       | Runs once `pyproject.toml` exists                 | `pytest`                                                              |
| Formatting (prettier)       | Formatting of HTML, CSS, JS, JSON, YAML, Markdown | `npx prettier@3.3.3 --write .`                                        |
| Workflows (actionlint)      | GitHub Actions workflows, including shell scripts | Read the error in the CI log                                          |
| Secrets (gitleaks)          | Leaked keys or tokens anywhere in git history     | Remove the secret and rotate it                                       |
| Site build                  | The website builds with your changes              | `python3 .github/pages/build.py _site`                                |
| App (npm lint, test, build) | Runs once `web/package.json` exists               | `cd web && npm run lint && npm test && npm run build`                 |

Code conventions:

- Code, commit messages and pull requests are in English.
- No comments in code.
- Website content is in Polish.
- Editor settings come from `.editorconfig`: UTF-8, LF, 2-space indent (4 for Python).

Never commit API keys. Copy `.env.example` to `.env` and fill it in; `.env` is ignored by git. Share keys outside public channels.

## The app

The app lives in `web/`. Use Node.js 22, like CI: on Node 20 the test runner fails to start its workers.

- Plain HTML, CSS and JS files in `web/` are published as they are.
- If `web/package.json` exists, CI runs `npm ci` and `npm run build` and publishes `web/dist`.
- The build gets the site base path in the `BASE_PATH` environment variable, for example `/opendatahackathon42/dev/`. Configure your build tool to use it so links and assets work under both URLs.
- Add `lint` and `test` scripts to `web/package.json` and CI will run them.

## Deployment

Deployment is automatic. Every push to `development` or `release` runs the **Pages** workflow. It builds both sites and publishes them:

- `/` from `release`
- `/dev/` from `development`

A branch without a `web/` directory shows a placeholder page.

### Which version is live?

Each site has a `version.json` with the branch, commit and build time:

```bash
curl -s http://ggrzesiek.dev/opendatahackathon42/version.json
curl -s http://ggrzesiek.dev/opendatahackathon42/dev/version.json
```

Compare `commit` with the branch:

```bash
git fetch
git rev-parse origin/release origin/development
```

If they differ:

1. Open **Actions → Pages** and check that the latest run succeeded. Its summary shows what was published.
2. If the run succeeded, wait. GitHub Pages and your browser cache pages for up to 10 minutes. Use Ctrl+Shift+R or a private window.

## Promoting to production

Promotion is automatic. When CI passes on a push to `development` (that is, after a PR is merged), the **Promote to
release** workflow fast-forwards `release` to the commit CI tested. The Pages workflow then deploys `/`. A merged PR
reaches production a few minutes after it reaches `/dev/`.

The workflow:

- checks that the commit is on `development` and `release` can be fast-forwarded to it
- skips the commit if `release` already contains it, for example when an older CI run finishes after a newer one
- moves `release` to that commit and tags it `release-YYYY-MM-DD-HHMMSS`
- lists the promoted commits in the run summary

If CI fails on `development`, nothing is promoted and production keeps the last passing version.

To promote by hand, for example after a failed run was fixed by rerunning it:

- on GitHub: **Actions → Promote to release → Run workflow**, or
- from a terminal: `gh workflow run promote.yml`, optionally with `-f sha=<commit>` for a specific commit from
  `development`

`release` gets exactly the same commits as `development`; nothing is rewritten. The promotion fails if `release` has
commits that are not on `development`.

## Troubleshooting

- **Formatting check failed.** Run the fix command from [Checks](#checks), commit and push.
- **PR cannot be merged: branch is out of date or has conflicts.** Rebase on `origin/development`, resolve conflicts, then `git push --force-with-lease`.
- **I pushed to the wrong branch or cannot push to `development`.** Direct pushes are blocked. Push to a feature branch and open a PR.
- **The site shows an old version.** See [Which version is live?](#which-version-is-live).
- **Promotion failed with "cannot fast-forward".** Someone changed `release` outside the workflow. Ask the repository admin.
